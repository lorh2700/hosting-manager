# 현재 ERD 및 불필요 코드 검토

2026-10-05 · anti-slop **after**, 사용자 지정.

대상은 현재 `hosting-manager`의 Prisma/SQL 스키마, 분리 중인 `services/api`·`packages` 백엔드, 별도 저장소 `hosting-manager-web`이다. 기존 Next.js 전체 화면을 모두 실행한 종합 검사는 아니다. 소스와 연결 DB의 메타데이터를 읽어 대조했으며 실제 고객 데이터 행은 조회하지 않았다. 애플리케이션 코드, DB, 운영 배포는 변경하지 않았다. 이 보고서와 ERD 문서만 작성했다.

프로젝트 `AGENTS.md`에 따라 anti-slop은 주석·UI·문구에 적용한다. 미사용 함수·라우트·스키마 차이는 **일반 코드 검토** 결과이며, 해당하지 않는 R-XX 위반으로 표시하지 않는다. After 모드의 번호별 검토 결과로 기록하며 자동 삭제는 하지 않았다.

## 1. P1 · 필요한 DB 구조가 미적용이고 준비 상태 검사 범위가 부족함

분류: 일반 코드 검토 / 배포 준비.

- **연결 DB에 없는 테이블 7개:** `staff_merges`, `inventory_snapshots`, `inventory_count_records`, `backend_commands`, `backend_reservation_commands`, `backend_reservation_annotations`, `backend_guest_notes`.
- **투어 예약 차이:** `tour_bookings.requested_date`, `requested_time` 컬럼이 없고 `schedule_id`는 DB에서 NOT NULL인데 소스는 선택값으로 정의한다.
- 재고 조회·기록은 누락된 두 재고 테이블을 직접 사용한다. 숙소를 선택한 재고 조회와 저장이 영향을 받는다: [field-operations/service.ts:67](../packages/domain/field-operations/service.ts#L67).
- 준비 상태 검사는 사용자·사업자 및 새 백엔드 테이블 4개만 검사한다: [runtime.ts:74](../services/api/runtime.ts#L74). 현재 누락된 백엔드 테이블 때문에 실패하는 것이 맞지만, **신규 백엔드 마이그레이션만 적용하면 재고 테이블이 없어도 이 검사는 통과할 수 있다.** 현재 운영 장애를 재현했다는 뜻은 아니다.

제안: 마이그레이션 이력과 현재 구조를 함께 검토하고 아래 누락 구조를 순서대로 적용하는 배포 절차를 먼저 마련한다. 재고 등 활성 기능의 필수 구조도 준비 상태 검사 또는 배포 전 검사에 포함한다. 기존 DB에 중복 객체가 있을 수 있으므로 전체 마이그레이션을 무조건 재실행하지 않는다.

| 구조 | 해당 마이그레이션 |
| --- | --- |
| 직원 병합 이력 | `20260917010000_staff_merge_audit` |
| 투어 예약 문의 | `20260918010000_tour_booking_inquiries` |
| 재고 현황·기록 | `20261002010000_inventory_counts` |
| 공통 변경 명령 | `20261005010000_backend_commands` |
| 예약 명령·메모·고객 메모 | `20261005150000_reservation_workflows` |

## 2. P2 · 교체된 직원 관리 경로가 화면·서버·테스트에 남아 있음

분류: 일반 코드 검토 / 미사용·도달 불가 코드.

- 프론트엔드 [Management.tsx:37](../../hosting-manager-web/src/pages/Management.tsx#L37)의 옛 `StaffPage`는 현재 화면 경로에서 사용하지 않는다. 실제 직원 화면은 [App.tsx:14](../../hosting-manager-web/src/App.tsx#L14)의 `pages/Staff.tsx`다. 저장된 빌드 산출물에도 옛 화면의 고유 안내 문구와 export가 남아 있다.
- 프리뷰 [preview-management.ts:63](../../hosting-manager-web/server/preview-management.ts#L63)의 `GET /staff`는 먼저 등록된 [preview-people-events.ts:98](../../hosting-manager-web/server/preview-people-events.ts#L98)가 응답하므로 도달하지 않는다. 등록 순서: [preview.ts:117](../../hosting-manager-web/server/preview.ts#L117).
- 백엔드 [reads/service.ts:110](../packages/domain/reads/service.ts#L110)의 옛 `staff()`와 [runtime.ts:58](../services/api/runtime.ts#L58)의 분기는 현재 직원 조회가 workflow 경로를 타기 때문에 사용하지 않는다. 실제 경로는 `backend-routes.ts` → `application.ts` → `workflows.ts` → `people-events/service.ts`의 `listStaff`다.
- 옛 경로를 위한 `StaffPageQuery`, [read-repository.ts:44](../packages/data/read-repository.ts#L44)의 조회 함수, `tests/backend-reads.test.ts:295` 부근 테스트도 정리 대상이다.

영향: 어느 코드가 실제 권한·직원 동작을 결정하는지 혼동하기 쉽고, 사용하지 않는 경로의 테스트가 통과해도 실제 화면의 정확성을 보장하지 못한다.

제안: 옛 직원 경로만 제거하고 필요한 테스트 시나리오는 현재 직원 서비스로 옮긴다. 새 직원 화면이 재사용하는 `StaffSummary`, `StaffEditorResource`와 `Management.tsx`의 다른 화면은 유지한다. `StaffPageData`는 옛 화면과 함께 제거할 수 있다.

## 3. P2 · 별도 권한 범위 계산 함수가 실제 요청에 연결되지 않음

분류: 일반 코드 검토 / 테스트에서만 사용하는 구현.

- [identity/access.ts:101](../packages/domain/identity/access.ts#L101)의 `resolveOperationalScope()`는 실제 요청 처리부에서 호출하지 않고 `tests/backend-identity.test.ts:142` 이후 테스트에서만 사용한다.
- 이에만 연결된 `BackendOperationalScope`, `IdentityRepository.findOrganizationProperties`, [identity-repository.ts:38](../packages/data/identity-repository.ts#L38)도 같은 정리 후보이다.
- 실제 서비스는 [reads/policy.ts:25](../packages/domain/reads/policy.ts#L25)의 `moduleAllowed()`·`propertyScopeWhere()` 등으로 접근 범위를 제한한다.

영향: 실제 기능에 적용되지 않는 권한 함수를 검증하면서 권한 경계가 충분히 검증됐다고 오해할 수 있다.

제안: 실제 정책 함수를 기준으로 통합하거나 미사용 구현을 제거하고 사업자·숙소·역할 경계 테스트를 실제 요청 경로에 유지한다. 메뉴 노출, 서버 인증, 서비스 권한 재검사는 각각 목적이 있으므로 중복이라는 이유로 삭제하지 않는다.

## 4. P3 · 사용하지 않는 공개 상수·타입·함수

분류: 일반 코드 검토 / 정리 후보.

현재 검색 범위에서 정의 외 사용처가 없는 항목:

| 위치 | 항목 | 권고 |
| --- | --- | --- |
| `packages/contracts/field-operations.ts:28` | `FIELD_COMMAND_OPERATIONS` | 실제 `workflow.${route.id}` 명명과 별도이므로 제거 검토 |
| `packages/contracts/people-events.ts:5` | `PEOPLE_EVENT_UPLOAD_BODY_BYTES` | 실제 요청 크기 제한과 연결하거나 제거 |
| `packages/domain/reservations/policy.ts:20` | `reservationCapabilities()` | 실제 권한 계산 경로를 기준으로 통합 또는 제거 |

공개 export는 TypeScript 미사용 검사만으로 잡히지 않는다. 삭제 전 외부 패키지 소비자가 없는지 다시 확인하고 관련 빌드를 검증한다. 이번에는 패키지 외부 사용까지 없다고 단정하지 않는다.

## 5. P3 · 같은 직원 역할을 두 이름으로 표시

분류: 제품 문구 일관성 / 개선 권고. 특정 anti-slop 하드 게이트 위반으로 판정하지 않음.

- [navigation.ts:22](../../hosting-manager-web/src/lib/navigation.ts#L22): `cleaner` → “청소 매니저”.
- [management-types.ts:22](../../hosting-manager-web/src/lib/management-types.ts#L22): 같은 역할 → “청소 담당자”.
- 전자는 앱 메뉴·계정 영역, 후자는 직원 관리·권한 편집에서 사용한다.

제안: 사용자에게 보여 주는 역할 이름을 한 정의에서 재사용한다. 역할 ID나 접근 정책 변경은 필요하지 않다.

## 삭제 대상으로 보지 않은 항목

- `lib/operations-settings-store.ts`와 백엔드 연결 어댑터: 기존 서비스에서 계속 사용한다.
- 서버 권한 재검사, 중복 명령 방지, 동시 수정 방지, 변경 기록: 다른 경계를 보호하는 코드다.
- 프리뷰 데이터·서버: 실제 서비스 경로와 분리돼 있으며 화면 검증에 사용한다. 폴더가 크다는 이유만으로 삭제하지 않는다.
- DB에만 있는 객실 패드 및 이관·보관 테이블 12개: 다른 기능이나 이력에 사용될 수 있으므로 Prisma에 없다는 이유로 삭제하지 않는다.
- 제약·재시도·개인정보·이력 보존 이유를 설명하는 주석: 의미가 있어 유지한다. 이번 범위에서 별도로 삭제할 수준의 무의미한 주석은 확인하지 못했다.

## ERD와 확인 범위

- [인터랙티브 ERD](../docs/architecture/current-erd.html): 업무별 보기 10개, 전체 테이블 검색, 확대, 테이블 전체 컬럼·관계 확인.
- [Mermaid 원본 및 구조 목록](../docs/architecture/current-erd.md).
- 코드 정의 52개 = Prisma 모델 49개 + SQL 전용 테이블 3개. 실제 연결 DB는 public 테이블 57개·외래키 54개. 소스와 DB 합집합 64개를 문서에 포함했다.
- 외래키와 프로그램에서만 검사하는 논리 참조를 구분했다. 없는 테이블·컬럼은 미적용으로 표시했다. JSON 내부 구조와 실제 데이터 값은 포함하지 않았다.
- 연결 DB 확인은 읽기 전용 트랜잭션에서 시스템 메타데이터를 조회한 뒤 롤백했다. 이 결과는 **연결된 DB의 확인 시점** 기준이며, 모든 배포 환경이 동일하다는 뜻은 아니다.
- 백엔드의 엄격한 TypeScript 미사용 지역변수·매개변수 검사 통과. 프론트엔드의 추가 미사용 검사에서는 `server/preview-management.ts:61`의 사용하지 않는 `req` 매개변수 1건이 나왔다. 일반 빌드 실패를 의미하지 않는다.
- 전체 애플리케이션 테스트·운영 배포·실제 관리자 데이터 변경은 실행하지 않았다. 제품 전체 UI의 접근성·반응형 통과를 주장하지 않는다.
- 새 ERD 문서는 브라우저에서 업무별 보기 10개, 재고 테이블 검색, 컬럼 상세, 논리 관계 표시 전환, 확대, Enter 키로 테이블 선택을 확인했다. 390px 화면에서 문서 전체 가로 넘침을 수정하고 재확인했으며, 큰 관계도와 컬럼 표는 내부 스크롤을 제공한다. 확인 범위에서 브라우저 오류 로그는 없었다.

권장 순서는 **1번 DB 정합성 확인 → 2·3번 실제 경로 기준 코드 정리 → 4·5번 정리**다.
