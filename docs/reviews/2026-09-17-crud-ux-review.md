# CRUD·UX 코드 검토 — 2026-09-17

CRUD API는 대부분 존재하지만, 권한 검사·상태 전이·화면/API 계약에 결함이 있어 완성 상태로 판단하기 어렵다. 특히 메시지 권한과 투어 재고, 결제 예약 변경 보호를 먼저 보완해야 한다. 이번 작업은 검토이며 제품 코드나 운영 DB를 수정하지 않았다.

## 범위와 검증

- 전체 경로 목록화: 페이지 52개, API route 파일 107개, 직접 export된 HTTP 핸들러 180개. [API 전체 목록](./api-inventory.md).
- 주요 경로 정적 검토: 직원/초대, 숙소/채널/연동, 예약/달력, 청소/신청/문제 신고/비품, 메시지/자동답변 설정, 세탁, 투어/예약/운영업체, 결제·공개 API의 일부 경계.
- `npm test`: 기존 테스트 225개 통과.
- `node node_modules/typescript/bin/tsc --noEmit --incremental false --allowImportingTsExtensions`: 통과. 테스트 파일의 TS 확장자 import를 허용하는 옵션을 사용했다.
- `scripts/review-crud-repro.ts`: 실제 라우트 함수를 기존 인증/DB 테스트 대역으로 실행하여 아래 5개 관찰을 재현했다. 운영 네트워크·DB·실제 고객 발송은 사용하지 않았다.
- 브라우저 로그인 후 실제 화면 크기별 조작, 실제 PostgreSQL 동시 요청, SOLAPI/Beds24/결제의 실제 전송은 이번 검토 범위에 포함하지 않는다. UX 의견은 화면 소스와 요청/응답 흐름에 근거하며 시각적 완성도 검증은 별도다.
- 기존 테스트 통과는 아래 미검증 경로가 안전하다는 의미가 아니다. 투어 권한 함수는 기존 인증 대역에서 항상 null을 반환하므로 일반 테스트 대역만으로 투어 정상 쓰기 경로까지 검증했다고 볼 수 없다.

## 우선 수정할 문제

### R1 · P1 · 메시지 생성의 숙소 권한 검사를 생략할 수 있음 — 재현

근거: `app/api/messages/route.ts:39`, `:43`.

`propertyId`가 있을 때만 `requireManage`를 호출하고, `eventId`가 가리키는 예약의 숙소는 검사하지 않는다. 청소 직원이 propertyId 없이 다른 숙소 eventId를 보내면 201로 메시지가 저장된다. 관리 가능한 p1을 보내면서 p2의 eventId를 연결하는 것도 막지 않는다. sender도 클라이언트 값을 사용하므로 host 메시지처럼 저장할 수 있다. 외부 발송을 재현한 것은 아니지만 내부 대화 기록의 무결성이 깨진다.

수정 방향: eventId에서 실제 propertyId를 조회하고 관리 권한을 검사하며, 요청의 propertyId와 일치시킨다. 예약 없는 메시지도 명시적인 관리 가능 숙소를 요구한다. 발신자/유형은 서버에서 결정한다.

### R2 · P1 · 청소 직원의 숙소 배정을 해제해도 고객 메시지가 계속 노출됨 — 재현

근거: `app/api/messages/route.ts:17`.

조회 범위가 현재 UserProperty가 아니라 해당 직원의 모든 과거 청소 기록으로 정해진다. 현재 담당 숙소가 0개여도 2020년 청소 이력이 있는 p2의 새 메시지가 200으로 반환되었다. 퇴사·담당 변경 시 배정 해제만으로 접근 권한을 회수할 수 없다.

수정 방향: 현재 유효한 숙소 범위를 먼저 제한한 후 필요한 업무 범위와 교집합을 구한다. 과거 청소 이력을 현재 고객 대화의 접근 권한으로 사용하지 않는다.

### R3 · P1 · 결제 예약 날짜 수정 보호가 start/end 별칭에서 빠짐 — 재현

근거: `app/api/events/route.ts:11`, `:89`.

입력 정규화는 startDate/start 및 endDate/end 모두 허용하지만 결제 주문 확인은 원본 body.startDate/body.endDate만 검사한다. 동일한 결제 예약에 startDate를 보내면 409, start를 보내면 200으로 날짜가 수정되었다. 결제된 숙박 기간과 내부 달력이 불일치할 수 있다. 현재 UI가 이 별칭을 사용하는지는 별도이며 API 자체의 우회 경로다.

수정 방향: 원본 body가 아니라 정규화된 data의 날짜/type 변경 여부로 결제 보호를 적용한다.

### R4 · P1 · 투어 취소·복구 시 예약 인원 집계가 깨질 수 있음 — 코드 확인

근거: `app/api/tour-bookings/route.ts:128`, `:133`, `:142`.

취소 전 상태를 트랜잭션 밖에서 읽고 매번 인원을 차감한다. 두 담당자가 동시에 취소하면 둘 다 이전 상태를 읽어 정원이 두 번 복구될 수 있다. 또한 cancelled를 confirmed 등으로 PUT하면 bookedCount를 다시 증가시키거나 잔여석을 확인하지 않는다. 취소 복구 버튼은 현재 화면에 없지만 API는 허용한다.

수정 방향: 조건부 상태 변경 성공 건수에 따라 재고를 한 번만 변경한다. 취소 복구는 거부하거나 동일 트랜잭션에서 정원 확인과 재확보를 수행한다. 실제 DB 동시 취소 회귀 테스트가 필요하다.

### R5 · P2 · 통합 계정의 기존 DELETE가 청소 담당자 이력을 끊음 — 코드·스키마 확인

근거: `app/api/users/[id]/route.ts:16`, `:18`, `prisma/schema.prisma:532`.

cleaner 역할만 삭제를 막고 admin/manager는 직접 삭제한다. 통합 후에는 매니저·관리자도 청소 담당자이므로 해당 사용자를 삭제하면 cleanings.cleaner_id가 SET NULL로 바뀐다. 소유 숙소/초대 등의 외래키가 있으면 반대로 일반 500으로 실패할 수도 있다. 직원 UI에서는 삭제 대신 중지를 쓰지만 이전 API는 살아 있다.

수정 방향: 역할과 관계없이 동일한 비활성화 정책을 적용한다. 이력이나 통합 대응표가 존재하는 사용자는 hard delete를 막고 구형 endpoint도 명시적으로 종료한다.

### R6 · P2 · 매니저 화면의 청소 신청 거절이 403으로 실패 — 재현

근거: `app/api/cleaning-applications/route.ts:130`, `app/admin/cleaning-requests/page.tsx:108`, `components/sidebar.tsx`의 매니저 메뉴.

화면은 매니저에게 배정 숙소의 신청 관리 및 거절 버튼을 제공한다. PUT은 관리자가 아닌 경우 신청자 본인만 허용하므로 자신의 담당 숙소에 온 다른 직원의 신청을 거절하지 못한다. p1 매니저가 p1의 다른 직원 신청을 거절하면 403을 반환했다. 신규 신청은 즉시 배정되지만 기존 pending 신청에는 이 화면 경로가 남아 있다.

수정 방향: 숙소 관리자의 승인/거절과 신청자 본인의 취소를 다른 권한·상태 전이로 처리한다. 즉시 배정 방식에서 남아 있는 ‘승인 대기’ 화면과 문구도 정리한다.

### R7 · P2 · 미배정 청소가 신청 화면에서 사라짐 — 코드 확인

근거: `app/cleaner/schedule/page.tsx:33`, `app/api/cleanings/route.ts`의 GET/POST, `app/api/cleaning-applications/route.ts`의 POST.

API는 ‘신청 가능 = 배정자 없음’으로 판단하고 isOpen을 레거시 플래그로 설명한다. 그러나 화면은 c.isOpen까지 참이어야 표시한다. 수동 생성 또는 배정 해제된 isOpen=false 일정은 미배정인데도 신청할 수 없는 것처럼 보인다.

수정 방향: 신청 가능 조건을 한곳에서 정의하고 서버/화면에 공통 적용한다. 완료·과거 일정·동일 날짜 중복 슬롯 조건도 함께 맞춘다.

### R8 · P2 · 동기화 이력 화면이 실제로 연동 설정을 조회함 — 재현

근거: `app/admin/integrations/page.tsx:95`, `app/api/integrations/route.ts:5`.

화면은 `/api/integrations?type=sync_logs&limit=50`을 호출하지만 API는 type/limit을 무시하고 integration 목록을 반환한다. 테스트에서도 real-log가 아니라 integration이 반환되었다. UI는 이를 성공/실패·생성/수정/삭제 건수로 렌더링해 잘못된 경고와 빈 수치를 보여준다. 실제 SyncLog의 result JSON과 화면이 기대하는 평탄한 필드 간 변환도 필요하다.

수정 방향: 전용 이력 API와 명시적인 응답 타입/범위/정렬/제한을 구현한다.

### R9 · P2 · 업체 전달 실패·설정 누락도 ‘전달완료’로 저장됨 — 코드 확인

근거: `app/api/tour-bookings/[id]/forward/route.ts`, `lib/notify.ts:413`.

운영업체 없음, 알림 꺼짐, 템플릿/연락처 누락이면 알림 함수가 정상 반환한다. 실패 결과를 검사하지 않고 예외도 내부에서 삼킨다. 호출 라우트는 그대로 status=forwarded를 저장하므로 운영자가 실제로 전달됐다고 오해한다. 확정된 예약을 재전달하면 confirmed 상태도 forwarded로 덮어쓴다.

수정 방향: 예약 상태와 전달 상태를 분리하고 accepted/failed/skipped/unknown을 구분한다. 접수 실패를 ‘전달완료’로 표시하지 않는다.

### R10 · P2 · 투어 예약의 언어·미팅 요청·티켓 구분이 관리 화면에서 누락됨 — 코드 확인

근거: `app/api/public/tour-bookings/route.ts`의 생성 data, `app/api/tour-bookings/route.ts:23`, `app/admin/tour-bookings/page.tsx`의 TourBooking/렌더링.

고객이 입력한 language, meetingChoice, meetingDetail, tickets는 DB에 저장되지만 관리자 목록 DTO와 화면에 없다. 운영업체 전달도 기본 tour.meetingPoint만 사용한다. 고객이 선택한 픽업/미팅 요청과 티켓 구성을 담당자가 확인하기 어렵다.

수정 방향: 관리자 상세에 수집한 항목을 모두 노출하고 전달 메시지 또는 연결된 상세 화면에서도 확인 가능하게 한다.

### R11 · P2 · 조회 실패가 ‘자료 없음’으로 표시됨 — 화면 코드 확인

근거: `app/admin/supplies/page.tsx:30`, `app/admin/issues/page.tsx:31`, `app/admin/tour-bookings/page.tsx`의 fetchBookings, 숙소 설정의 fetchProperty.

일부 화면은 res.ok 검사 없이 JSON을 배열로 취급하거나 실패를 console.error로만 처리한다. 세션 만료·서버 오류 시 로딩이 끝난 후 빈 목록 또는 ‘숙소를 찾을 수 없습니다’가 보여 정상적인 빈 결과처럼 보인다. 저장 실패도 서버의 구체적인 사유를 버리는 화면이 있다.

수정 방향: 오류/빈 결과/권한 없음 상태를 분리하고 재시도 버튼을 제공한다. 공통 API 래퍼에서 상태코드와 서버 메시지를 보존한다. 직원 관리 화면의 명시적 오류·재시도 패턴을 다른 화면에도 적용할 수 있다.

## CRUD 구현 현황

‘있음’은 해당 동작의 코드가 있다는 뜻이다. 실제 DB·외부 서비스·브라우저 E2E까지 완료되었다는 뜻이 아니다. 이력성 업무에서 DELETE 대신 취소/종료/폐기를 쓰는 것은 누락으로 단정하지 않았다.

## UX 보완 제안 (확정 버그와 구분)

- 직원 상세에서 재발급 버튼을 누르기 전에 ‘기존 일정 링크 사용 불가’ 안내/확인을 제공한다. 로그인 중지와 공개 링크 폐기가 서로 다른 동작임을 함께 설명한다.
- 직원 상세·숙소 설정·자동답변 안내문에 미저장 변경 표시와 이탈 확인을 제공한다. 직원 선택을 바꾸거나 닫을 때 입력한 정보가 사라질 수 있다.
- 직원 상세의 ‘복사’도 공통 action 때문에 ‘저장했습니다’라고 표시되고 전체 목록을 새로 읽는다. 복사는 ‘복사했습니다’, 실제 변경은 ‘저장했습니다’로 분리한다.
- 화면에 보이는 작업 버튼과 API 권한을 같은 기준으로 맞춘다. 예를 들어 일반 배정 매니저에게 숙소 삭제 버튼을 보여준 후 서버에서 거절하는 흐름을 피한다.
- 전화번호 로그인 직원의 빈 이메일 필드를 일반 이메일 입력처럼 보여주는 대신 ‘전화번호 로그인’과 ‘이메일 로그인 변경’을 구분한다.
- 청소 직접 배정/즉시 신청/과거 승인 대기가 섞여 있으므로 상태명·성공 메시지·취소 경로를 일관되게 정리한다.

## 수정 순서

1. R1/R2/R3 권한 및 보호 조건 수정 + 재현 시나리오를 기대 보안 동작을 검증하는 테스트로 전환.
2. R4 투어 상태 전이/재고 동시성 및 R5 이력 보존 정책.
3. R6~R10 업무 흐름·조회 계약·전달 결과·운영 정보 누락 수정.
4. R11 공통 오류 UI와 미저장/재발급 UX 보완.
5. 별도 테스트 데이터로 관리자·매니저·청소 직원 각각의 모바일/데스크톱 전체 흐름 확인. 외부 발송은 테스트 수신자만 사용.
