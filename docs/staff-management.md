# 직원 통합 — users 기준

## 최종 모델

- `users`가 이름·전화번호·로그인·역할·알림·개인 일정 링크의 유일한 운영 원본이다. `canClean` 또는 청소 프로필 생성 절차는 없다.
- `role`: 관리자(admin), 매니저(manager), 청소 담당자(cleaner). 세 역할 모두 청소 담당자 후보가 된다. active/no_account 직원만 신규 배정할 수 있다.
- `user_properties`는 관리·청소에 공통으로 사용하는 담당 숙소다. 관리자는 전체, 나머지 역할은 명시적 배정만 접근한다. 빈 배정은 접근 없음이다.
- 매니저는 직원 관리와 직접 청소를 모두 수행한다. 청소 전용 직원은 본인 청소 완료·문제 상태만 수정할 수 있고 예약 관리 권한은 없다.
- `users.owner_id`는 매니저가 등록한 청소 직원을 관리할 수 있도록 하는 소유 관계다. 숙소 접근 권한은 이 값에서 추론하지 않는다.
- 로그인 없는 직원도 users에 존재한다. `status=no_account`, 사용할 수 없는 비밀번호, 내부용 이메일을 부여한다. 비밀번호 발급 또는 이메일 초대 수락은 같은 User row를 활성화한다.
- `cleanings.cleaner_id`와 `invitations.cleaner_id`는 호환성을 위해 이름만 유지하며 **users.id**를 참조한다. 외부 파트너가 저장한 이전 Cleaner ID는 `staff_identity_map`으로 변환해야 한다.
- `/api/cleaners` 및 `staffDirectory`는 기존 클라이언트의 name/cleanerId 형식을 위한 호환 인터페이스다. cleaners 테이블을 조회·수정하지 않는다. 직원 API에 비밀번호를 반환하지 않는다.
- 기존 청소 역할 추가·프로필 연결·계정 병합 API는 410을 반환한다. 화면에서 해당 기능을 제거했다.

## 화면

`/admin/staff`에서 한 직원당 한 row로 이름·전화번호·관리 역할·공통 담당 숙소를 설정한다. 관리자만 타인의 역할을 바꾸며, 매니저는 본인 정보와 본인이 등록한 청소 직원 정보를 관리한다. 본인 역할/상태/숙소 권한은 직접 확대할 수 없다.

청소 일정의 담당자 선택은 사용자 역할과 담당 숙소를 기준으로 한다. 매니저는 별도 등록 없이 `내 청소 업무`에서 신청·일정 확인·완료 처리를 할 수 있다. 신규 청소 알림과 체크아웃 알림도 동일 사용자 연락처와 숙소 배정을 사용한다.

## 운영 전환 절차

이 변경은 코드만 먼저 배포할 수 없다. 유지보수 시간에 쓰기를 중단하고, 백업 및 복원 가능 여부를 확인한 뒤 다음 순서로 진행한다.

1. `scripts/prepare-staff-identity.sql`로 기존 ID·연락처와 동일 연락처 후보를 검토한다. 이 스크립트는 대응표 생성 및 조회만 수행한다. 이름 또는 전화번호로 자동 병합하지 않는다.
2. 확인한 동일인만 `staff_identity_map(cleaner_id,user_id)`에 남길 기존 계정 ID를 명시한다. 이미 user_id로 연결된 프로필은 자동으로 해당 User를 사용한다. 연결되지 않은 프로필은 기본적으로 `staff-<기존 Cleaner ID>` User를 생성한다. 같은 사람의 별도 계정은 명시적 매핑 없이 자동 삭제하지 않는다. 한 User에 여러 프로필을 매핑하는 작업은 일정 링크 충돌 때문에 차단한다.
3. 매니저의 기존 청소 범위가 관리 범위보다 넓거나 두 전화번호가 다르면 운영자가 먼저 정리한다. 이관은 이를 임의로 덮어쓰거나 관리 권한을 확대하지 않고 전체 롤백한다.
4. 운영 연결을 확인한 상태에서 `npx prisma migrate deploy`를 실행한다. 미적용된 다른 마이그레이션도 실행되므로 목록을 먼저 검토한다. `20260917020000_users_staff_identity`가 실제 데이터 이관이며, 앞서 작성한 `20260917010000_staff_merge_audit`만으로는 통합되지 않는다.
5. 새 코드를 배포한다. 실제 직원의 전화번호·역할·담당 숙소·과거 청소·개인 링크·신규 배정·청소 완료를 확인한 뒤 운영을 재개한다. 이 작업에서는 운영 DB 실행·배포를 하지 않았다.

## 이관 보장 및 제한

### SQL 편집기 실행 및 실패 후 확인

수동 실행 시 `20260917020000_users_staff_identity/migration.sql`의 **전체 내용**을 한 번에 실행한다. 현재 파일은 단일 `DO $staff_identity$` 문으로 구성되어 자동 커밋 환경에서도 원자적으로 실행되며, 임시 테이블 `staff_old_scope`를 사용하지 않는다. 내부 구간만 선택해서 실행하지 않는다. 수동 적용 후 Prisma 이력은 실제 적용 완료를 확인한 뒤 별도로 맞춰야 한다.

이전 SQL에서 `staff_old_scope does not exist` 오류가 발생했다면 재실행 전에 `scripts/check-staff-identity-state.sql`을 실행한다. 트랜잭션 중단 상태 오류가 나오면 해당 세션에서 `ROLLBACK;` 후 조회한다. 구 테이블 두 개가 존재하고, legacy 테이블과 snapshot은 없으며, added_user_columns가 빈 배열이고 cleaning_assignee_table이 cleaners이면 이관 전 구조다(identity_map은 사전 준비로 존재할 수 있다). 일부 컬럼이나 snapshot만 남았다면 구 SQL 일부가 커밋되었을 수 있으므로 결과와 백업을 검토한 뒤 복구 방법을 정한다. 컬럼·테이블을 임의로 삭제하거나 중간 단계부터 재실행하지 않는다. 수정된 이관문은 이미 적용되었거나 일부 적용된 구조를 감지하면 변경 전에 중단한다.

### 데이터 보존

- users에 이미 있는 로그인 비밀번호·이메일·역할은 유지한다. 전화번호가 비어 있으면 기존 cleaners.phone을 채운다. 둘 다 존재하며 다르면 중단한다.
- 기존 CleanerProperty 및 ‘운영자 전체’ 범위는 청소 전용 직원의 명시적 UserProperty로 이관한다. 배정 없음은 빈 범위로 유지한다. 전체는 이관 시점의 숙소 목록으로 고정되므로 이후 신규 숙소는 별도 배정한다.
- 기존 관리자의 전체 권한과 매니저의 관리 배정을 기준으로 공통 범위를 정한다. 매니저의 옛 청소 범위가 이를 넘으면 중단한다.
- 청소 일정·초대 외래키를 사용자 ID로 치환한다. 명시적으로 합치는 청소 전용 로그인은 신청자·처리자·신고자 등 일반 actor ID 참조를 옮긴 뒤 삭제한다. 관리 소유권이 있는 원본 계정의 자동 삭제는 거부한다. 과거 JSON 이력의 스냅샷은 덮어쓰지 않으며 ID 추적은 대응표로 한다.
- 기존 개인 일정 토큰을 그대로 가져오고, 없던 직원에게는 새 토큰을 만든다. 로그인 중지와 일정 링크 폐기는 별개다.
- `legacy_cleaners`, `legacy_cleaner_properties`, `staff_identity_map`, `staff_identity_users_before`는 운영에서 사용하지 않는 이관·복구 자료다. 원본 계정 스냅샷에는 로그인 해시가 포함되므로 접근은 운영 DB 관리자에게 한정한다. 보존 기간 종료 후 별도 검증을 거쳐 제거한다. 기존 테이블은 즉시 파괴하지 않는다.
- 모든 변경은 하나의 SQL 트랜잭션이다. 실패 시 스키마/데이터가 함께 롤백된다. 성공 후 이전 앱으로 단순 롤백하면 ID가 맞지 않으므로 복원 시 백업으로 DB와 코드를 함께 되돌린다.
- 로컬 검증은 PGlite의 PostgreSQL 엔진으로 실제 이관·외래키·충돌 롤백을 실행한다. 운영 DB 전체 데이터에 대한 사전 검토를 대체하지 않는다.
