# 게스트 링크의 DB 검증 전환

2026-10-23 소스 변경. 이 문서는 운영 DB 적용이나 배포 완료를 의미하지 않는다.

## 구분

| 링크 | 발급·검증 방식 | 허용 범위 |
| --- | --- | --- |
| `/i/i2_...` | 16바이트 난수(128비트), SHA-256 해시로 DB 조회 | 지정된 예약·숙소, 발급 시 정한 만료까지 |
| 기존 `/guest/welcome/...` | 기존 암호화 주소와 `i1_` DB 토큰 모두 유지 | 원래 예약·숙소·만료 유지 |
| `/stay/:slug` | 공개된 고정 숙소 주소 | 진입 화면. 예약 정보와 기능은 기존 예약 확인·세션 검증 후 사용 |
| `/guest-checkout#q1_...` | 32바이트 난수, SHA-256 해시로 DB 조회 | 지정 숙소의 기존 퇴실 확인 절차 |
| 기존 암호화 초대장·서명 QR | 등록된 해시 우선 조회, 미등록 값만 기존 검증 후 등록 | 원래 예약·숙소·만료 유지 |

새 게스트 링크 발급에 별도 환경변수나 비밀키가 필요하지 않다. `JWT_SECRET`은 직원 로그인, 기존 세션·기기 검증 등에 여전히 필요하므로 삭제하지 않는다. 이미 DB에 등록된 링크는 이 값 변경에 영향을 받지 않는다. URL 자체는 소지자에게 권한을 주는 값이므로 코드·로그·공개 문서에 원문을 남기지 않는다.

## 데이터와 검증

마이그레이션 `20261013120000_guest_link_tokens`가 SQL 전용 테이블 `guest_link_tokens`를 만든다. Prisma 모델 생성이나 기존 테이블 변경은 필요하지 않다. 테이블에는 원본 토큰, 게스트 이름, 비밀번호를 저장하지 않는다.

- `token_hash`가 기본키이며 용도, 숙소, 예약 종류·ID, 만료, 폐기 시각을 저장한다.
- 발급 기록 저장에 실패하면 URL을 반환하거나 Beds24에 게시하지 않는다.
- DB에서 폐기·만료·다른 용도로 확인된 토큰은 기존 서명 검증으로 우회하지 않는다. DB 장애 때에도 검증을 생략하지 않는다.
- 동일 해시를 다른 예약·숙소로 옮기거나 만료를 연장하지 않는다. 폐기된 기록을 되살리지 않는다.
- 예약 취소·삭제, 숙소 불일치, 체크아웃 후 30일 제한은 실제 예약 조회에서 계속 검사한다.
- QR은 재발급해도 이미 발급된 다른 QR을 자동 폐기하지 않는다. 기존 인쇄물을 계속 사용할 수 있다.
- `anon`, `authenticated`, `PUBLIC`의 테이블 접근을 차단한다. 서버 DB 연결에서만 읽고 쓴다.

## 운영 적용 순서

2026-10-23 확인: Netlify 운영 배포는 `7703215`(10월 15일)이며 초대장 페이지는 아직 JWT 키로 검증한다. 로컬 운영 접속 설정으로 읽은 공유 DB에는 `guest_link_tokens`가 없었다. 새 발급기만 먼저 배포하면 안 된다. 아래 DB 준비와 게스트 페이지 배포가 선행되어야 한다.

새 주소는 `https://voidanchae.com/i/i2_` 뒤 난수 22자와 `?lang=en`까지 57자다. 코드에 예약 ID나 개인정보를 포함하지 않는다. 기존 긴 주소는 짧은 주소로 강제 전환하지 않으며, Beds24에 이미 저장된 유효한 주소도 교체하지 않는다.

1. DB 백업 후 **hosting-manager 소유 마이그레이션** `prisma/migrations/20261013120000_guest_link_tokens/migration.sql`을 기존 공유 DB에 한 번 적용한다. 모노레포 API 사본을 별도로 중복 실행하지 않는다. 빌드·시작 시 자동 마이그레이션은 추가하지 않았다.
   이후 `20261023010000_verified_invitation_recovery/migration.sql`을 적용한다. 이번에 검증한 기존 링크 한 건만 원래 예약·숙소·일정에 일치할 때 등록하며 만료를 연장하거나 폐기된 링크를 되살리지 않는다. 현재 코드에는 같은 해시의 정확 일치 복구도 포함되어 있다.
2. **먼저 Netlify의 hosting-manager**를 배포한다. `/i/[token]`과 기존 초대장 페이지는 같은 검증·화면을 사용한다. 새 토큰을 읽는 초대장 페이지·게스트 앱·체크아웃 처리와 Beds24 발급기가 같이 변경된다.
3. **그 다음 현재 API 배포 환경에 hosting-manager-platform/apps/api**를 배포한다. Cloud Run으로 이관 중이라면 실제 관리자 웹이 연결한 API를 기준으로 적용한다. 관리자에서 만드는 초대장·QR도 같은 DB 기록을 사용한다. 웹 UI 변경·환경변수 추가는 없다.
4. 아직 읽히지 않은 구형 링크를 보존하려면 아래 사전 등록 도구의 검토 결과를 확인한 뒤 적용한다. 등록되지 않은 구형 링크가 남아 있는 동안 기존 발급 키를 교체하지 않는다.
5. 관리자 테스트 예약에서 새 초대장 발급→페이지→이름 확인, 기존 발송 주소 열기, QR `status` 조회를 검증한다. 운영 예약에 체크아웃 확정이나 테스트 메시지를 보내지 않는다.

## 구형 링크 사전 등록

hosting-manager 폴더에서 Node 24와 설치된 의존성을 사용한다. 기존 `.env`/`.env.local`의 서버 설정을 읽고, 출력에는 토큰·URL·게스트 이름을 남기지 않는다.

```powershell
node scripts/backfill-guest-links.mjs
node scripts/backfill-guest-links.mjs --apply
```

첫 실행은 검토 모드다. 등록 가능한 건수와 확인이 필요한 항목을 보고 두 번째 명령을 실행한다. 검토 모드는 게스트 링크 발급 기록·예약·Beds24 Info Item을 변경하지 않는다. Beds24 읽기 인증 과정에서 기존 토큰 캐시가 갱신될 수 있다.

도구는 최근 30일 이후 체크아웃인 예약의 기존 `VOID_INVITATION`을 읽고, 검증된 참조를 실제 로컬·Beds24 예약과 대조한다. 메시지 전송, Info Item 수정, 새 초대장 발급은 하지 않는다. 현재 설정된 키로 검증 가능한 기존 숙소별 체크아웃 QR도 등록한다. 실패한 값의 예약을 임의로 추측해 등록하지 않는다.

**이미 키가 사라진 모든 구형 링크를 자동 복구할 수는 없다.** 이번 마이그레이션에는 이미 원래 예약·만료를 검증한 초대장 3건과 별하재 인쇄 QR 1건의 해시만 포함되어 있다. 그 밖의 미등록 구형 링크는 원본 URL과 발급 당시 키 또는 신뢰할 수 있는 발급 기록이 필요하다. Beds24에 남지 않은 수동 발급 링크는 최초 정상 접속 시 등록되므로 별도로 확인해야 한다.

## 폐기·장애·롤백

필요한 링크의 `revoked_at`을 서버 관리자 작업으로 설정하면 그 링크를 이용한 이후 접속을 거부한다. 이미 로그인한 게스트 앱 세션의 종료는 기존 게스트 접속 관리에서 별도로 처리한다. 현재 UI에 새 링크 폐기 화면은 추가하지 않았다. 미사용 발급 기록을 삭제해 폐기를 취소하거나 기존 서명 fallback을 다시 허용하지 않는다.

DB 장애는 서비스 오류로 처리되며 키 검증만으로 우회하지 않는다. 이 테이블도 기존 DB 백업 대상에 포함한다. 신규 난수 링크 발급 후에는 구형 수신 코드로만 롤백하면 해당 링크가 열리지 않는다. 수신 코드와 테이블을 유지한 채 발급을 중단하거나 수정 버전을 배포한다. 로그인 키 복원으로 되돌리는 방식은 사용하지 않는다.
